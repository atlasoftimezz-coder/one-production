============================

Platform: Windows 11 (native), single local machine, single user (MVP)


1. CONTEXT
----------
Today every YouTube episode is hand-driven through one long chat: script, voice clone,
read-check, mastering, subtitles, art or stock footage, edit. The pieces work (vo-app,
make_srt, stickvid, competitor benchmarking) but nothing coordinates them, quality checks
happen only when remembered, usage limits cut work off mid-task, and settings live in chat
history.

One Production is a LOCAL APPLICATION that fixes this:
- one chat box where you talk to a master assistant, which spawns worker chats and can
  check work with a different model
- any number of your own AI accounts (Claude logins, Codex logins, API keys), each with its
  own email
- a usage page, and an automatic handoff when an account runs low or hits its limit: all
  context saved to a handoff file, work continues on the next account
- production tools inside the chat, starting with the voiceover pipeline
- local and cloud MCP tools, and storage for any kind of file

It runs locally because Chatterbox, the voices and the files are all on this machine.

3. KEY DECISIONS
----------------
D1 Windows-native, no Firstmate.
   Firstmate is macOS/Linux only. On this PC: claude, codex and gh are installed natively;
   WSL has only the docker-desktop distro. Firstmate would need Ubuntu in WSL plus a second
   login for both CLIs. Its two useful ideas are rebuilt inside the project:
   - dev\dispatch.json + dev\dispatch.py: rules pick claude or codex per coding task and
     move to the next one when an account runs low
   - cross-model review: a change written by Claude is reviewed by Codex, and the reverse;
     notes saved to dev\reviews\<task>.md

D2 Every account is used only through its official client.
   API key -> Anthropic API.  Claude login -> `claude -p`.  ChatGPT login -> `codex exec`.
   Login tokens are never extracted or reused in our own calls. Only accounts the user owns.

D3 App login and provider logins are separate layers.
   You log into One Production once. Each provider account keeps its own email.

D4 Free-first, paid tools optional.
   Editing defaults to ffmpeg; DaVinci Resolve MCP needs Resolve Studio. Stock defaults to
   free sources / code-drawn art; Storyblocks MCP needs a paid key.

D5 Clone the reference voice exactly.
   A voice the user supplies is reproduced as-is (clone_exact preset, grid_pad pace), never
   pitch-shifted toward a niche profile unless asked.

D6 React to limits; don't rely on predicting them.
   Subscription logins publish no reliable % used, so the switch has two triggers:
   - PRIMARY (reactive): the CLI/API returns a rate-limit / usage-limit error -> handoff
   - SECONDARY (predictive): estimated usage crosses the threshold -> offer handoff
   API keys have exact usage, so for them the predictive trigger is reliable.

D7 Terms first, then rotation.
   Switching between accounts is for continuity of work, not for getting around limits.
   Default switch order goes subscription -> API key (pay-per-use) rather than chaining
   several subscriptions. Chaining subscriptions stays OFF until R8 is confirmed.

D8 Many users = many installs, not one shared server.
   Every friend installs One Production on their own PC: own accounts, own files, own GPU,
   own usage page. Nothing is shared and nobody runs on someone else's accounts. This keeps
   "for other users too" without building a hosted multi-tenant service. (A hosted version
   is a separate future project.)

D9 Assume a brand-new user with nothing installed.
   No Chatterbox, no voices, no ffmpeg, no CLIs, maybe no NVIDIA GPU. The app must detect
   what exists, install what's missing only with consent, and switch off modules the PC
   can't run - never crash or silently fail because something is absent.

---------------
R1 ACCOUNTS
  - Add any number of: Claude logins, Codex/ChatGPT logins, Anthropic API keys
    Each may use a different email. ChatGPT is used only through Codex
    logins - no OpenAI API keys (user, 2026-10-05).
  - Each account isolated:
      Claude  -> own folder, launched with CLAUDE_CONFIG_DIR=profiles\claude-<n>
      Codex   -> own folder, launched with CODEX_HOME=profiles\codex-<n>
      API key -> Windows Credential Manager (python keyring), never in a file

                (loggedIn, authMethod, email, orgName, subscriptionType, configDirectory -
                 verified on Claude Code 2.1.284)
      Codex  -> typed by the user once (`codex login status` prints no email, v0.157.1)
      API    -> user label + last 4 characters of the key
  - "Add account" opens the provider's own login inside a fresh folder.
  - Remove, re-login, disable per account. Health badge (green/red) at startup.
  - Monthly reset day per account (the allowance cycle from Note 1).

R2 USAGE PAGE
  - One card per account: provider, label, plan type, status, % used bar, tokens in/out,
    estimated cost (API), request count, last used, reset time, and a tag:
    EXACT (API keys) or ESTIMATED (subscription logins).
  - Time ranges: today / 5 hours / 7 days / this month.
  - Totals across accounts; breakdown by project, by model, by worker.
  - Thresholds per account: warn at 70%, offer switch at 85% (editable).
  - Switch order: drag-to-reorder list; both triggers (D6) follow it.
  - Switch log: time, from -> to, trigger (limit error / threshold / manual), usage at
    switch, link to the handoff.md written.
  - Limit-hit log: every rate-limit error, with its raw message and the ESTIMATED % at that
    moment, to calibrate estimates.
  - Estimate accuracy shown per subscription account: over the last 7 days, the estimated %
    at each actual limit hit. TARGET: median within +/-10 points of 100% (i.e. estimate
    reads 90-110% when the real limit hits), and no hit below 70% estimated. Accounts
    outside target show "estimate unreliable" and the predictive trigger is switched off
    for them (reactive trigger still works). Estimator recalibrates its per-account budget
    from the log after each hit.
  - CSV export.

R3 HANDOFF AND BACKUP
  - handoff.md written: at every switch, every N turns, and on app shutdown.
    Contents: goal, decisions made, files touched (paths), open tasks, last 20 messages
    verbatim, partial last reply (if any), usage at switch.
  - Limit hit MID-RESPONSE: the partial reply is kept and marked "interrupted"; the handoff
    tells the next account to resume from that point, not to restart the task. Any tool
    action that was in flight is listed as "unconfirmed - verify before repeating".
  - Before switching: prompt "Another account available?" listing eligible accounts.
    If no account is eligible: save handoff, pause, show reset times.
  - One click: "continue on account X" - new session starts with handoff.md first.

R4 CHAT AND ORCHESTRATION
  - Chat with streaming replies, projects, history.
  - Master assistant (Opus) can spawn worker chats (Sonnet) per task.
  - Optional cross-model check: answer reviewed by a different provider.
  - Local OS MCP and cloud MCPs (through claude -p; registry file for the API path).
  - Storage per project for any file type: upload, list, preview, download.
  - CONCURRENCY: workers run in parallel, max N at once (default 3). Each worker is pinned
    to one account; the scheduler spreads workers across accounts by remaining headroom.
    Two workers never write the same file: file locks per project. GPU-bound tools
    (voiceover) are a single-slot queue.
  - PINNED WORKER HITS A LIMIT: the worker writes its own handoff (R3), releases its file
    locks, and is RE-PINNED to the next eligible account in the switch order, resuming from
    the handoff. Workers re-pin automatically (no prompt per worker); the master chat shows
    one notice listing every re-pin. If no account is eligible, the worker PAUSES with its
    handoff saved and resumes when an account resets or the user adds one. Pinning means
    "one account at a time, never two in parallel", not "one account forever".

R5 PRODUCTION TOOLS
  - Voiceover from chat ("voice this script with Human") -> vo-app job -> mp3 + SRT link.
  - Later workers: research, script, animation, video editor, packaging.

R6 SECURITY
  - Bind 127.0.0.1 only.
  - Per-session API token: generated at startup, required on every request (header);
    rejected requests logged. Delivery: the launcher opens
    http://127.0.0.1:<port>/#t=<token>; the page reads it from the URL fragment (never sent
    to the server, never in logs or history after the page clears it with
    history.replaceState) and keeps it in memory only. No endpoint ever returns the token,
    so another local page cannot fetch it. Reopening the tab = relaunch from the app/tray.
  - Host header must be 127.0.0.1 / localhost (blocks DNS rebinding).
  - Origin check + no permissive CORS (blocks cross-site requests from web pages).
  - Local OS MCP / shell / file-write outside projects\ = PERMISSION PROMPT per action,
    showing the exact command or path; "allow once / allow for this session / deny".
    Default deny for deletes, installs, network uploads.
    "Allow for this session" decisions are held in server memory only (never written to
    disk) and are cleared on restart; the UI lists active session allowances with revoke.
  - No secrets in files, logs or the repo; keys only in Credential Manager.
  - ONE redaction function (security\redact.py: API-key patterns, bearer/OAuth tokens,
    passwords, the session token) applied to: logs, handoff.md (incl. the 20 verbatim
    messages and the partial reply), switch log, CSV export, and every file added to a
    backup zip. Redacted spans read [REDACTED:<type>].

R7 APP LOGIN
  - Local profile login for MVP.
  - Google sign-in (OAuth desktop flow) later - needs the user's Google Cloud client ID.

R8 TERMS CHECK (gate before account rotation ships)
  - Read and record, per provider, what the current terms say about:
    scripted/automated use of the CLI with a subscription; holding several accounts;
    switching accounts when a limit is reached.
  - Result stored in docs\terms-check.md with links and date. Subscription chaining (D7)
    stays disabled unless every provider involved allows it.

R9 RELIABILITY
  - Errors classified: rate/usage limit -> handoff path (R3); network / 5xx / timeout ->
    retry with backoff (3 tries: 2s, 8s, 30s); auth error -> mark account red, ask user to
    re-login; bad request / tool error -> show to user, no retry.
  - Retry only if NO output tokens were received yet. If a transient error hits after the
    stream started, it is NOT re-sent: the partial reply is kept as "interrupted" and the
    task continues via the resume path (same account, prompt = "continue from here" +
    the partial text), so the original prompt is never billed twice. Tokens already
    streamed are recorded in the ledger before resuming.
  - Every call has a timeout; a stuck CLI process is killed and logged.
  - Retries never repeat a tool action that changes files without asking first.

R10 COST CAPS
  - Opus reviewer loops: max 2 review rounds per stage AND a token budget per review
    (default 40k input + 8k output per round, 120k total per episode stage), whichever
    hits first; then escalate to the user with the review so far.
  - Per-task and per-day spend cap (tokens and money) per account; reaching it pauses and
    asks. Caps shown on the usage page.

R11 BACKUPS OF PROJECT DATA
  - projects\ snapshot daily and before any bulk change: zip to a backup folder the user
    picks (default D:\Backups\one-production\), keep last 14.
  - Restore from the UI. Large media (audio/video) included by default, toggle to skip.

R12 GPU / HEAVY-JOB GATE (enforces D4 in code)
  - Every tool declares a cost class: light (CPU, seconds) / heavy (GPU or > 5 min) /
    download (model or large asset) / paid (external spend).
  - heavy, download and paid require an explicit confirm prompt showing what it will use
    (GPU, disk GB, money). Approvals can be remembered per tool.
  - Voiceover (Chatterbox) is pre-approved as heavy since the user chose it; nothing else is.

7. PHASES - EACH ONE CHECKED TWICE BEFORE THE NEXT STARTS
---------------------------------------------------------
12 phases (P0-P12). Each phase is small enough to test in one sitting and ends at a GATE:

  AUTO CHECK   - Claude runs the phase's test suite: `check.bat P<n>`
                 (pytest under tests\p<n>\ + scripted end-to-end runs). Produces
                 docs\gates\P<n>-auto.md: every check, pass/fail, numbers, logs. All must pass.
  MANUAL CHECK - you go through docs\gates\P<n>-manual.md: 5-10 plain tick-boxes
                 ("open the app, do X, you should see Y"), each with what to do if it fails.
  SIGN-OFF     - you write "P<n> approved" (or the failures) in docs\phase-log.md.
                 Next phase starts only after sign-off. A failed manual item becomes a fix
                 + a new automated test, so it can never silently come back.

Every phase also re-runs ALL earlier phases' auto checks (regression), so P6 green means
P0-P6 are still green.
